# Visual attributes

`visual_attribute_definitions` is a versioned taxonomy, not one database column per label. Each definition has key, version, name, description, category, BOOLEAN/ENUM/NUMBER/STRING type and allowed enum values. `POST /feedback/attributes` appends a definition version; old definitions are immutable. Initial categories include color, lighting, detail, technical, subject, composition, background, style, camera, mood and commercial properties.

The `visual-v1` deterministic extractor samples an image grid no larger than 256×256. Brightness is mean weighted sRGB luminance (0.2126 R + 0.7152 G + 0.0722 B)/255, not a calibrated physical luminance estimate. Contrast is its population standard deviation. Saturation is mean HSV saturation. Dark pixel ratio counts luminance below 0.1. Entropy uses 32 luminance bins in bits. Edge density counts adjacent horizontal samples differing by more than 0.15. Aspect ratio is original width/height. Dominant color is the largest coarse black/white/gray/red/green/blue pixel bin. Thresholds belong to extractor v1 and cannot silently change. Images are limited to 40 MB and 40 million decoded pixels; original SHA-256 must match before extraction.

Semantic extraction extends `VisionProvider.extractVisualAttributes`, separately from existing stock inspection and visual QA. TASK-03 stores the published `VISUAL_ATTRIBUTE_EXTRACTION` prompt. Strict output: `{features:[{key,value,confidence}],warnings:[]}`. Unknown/duplicate keys, wrong types, invalid confidence and attempts to replace deterministic measurements are rejected. Missing semantic attributes remain unknown, never false. The free provider deliberately returns a low-confidence mock style label and a visible warning; it does not pretend to recognize subjects. Real paid semantic extraction is disabled until a reviewed production adapter/call policy exists. Videos retain production context; semantic video/frame extraction is not invented.

Every `asset_visual_features` row references its extraction and taxonomy definition, records typed JSON value, confidence, source, requested/observed role, extractor version and provenance. Provider/model, prompt version and TASK-10 cost reference live on the extraction; each semantic feature also records its provider identity. Prompt variables from the immutable rendered snapshot populate REQUESTED_ATTRIBUTE separately. Model labels below the analysis confidence threshold (default 0.7) are excluded from analytical datasets unless a human override exists.

Extraction is cached by asset + extractor version. Repeating the same key creates no new features or charge. Explicit `visual-v1-rN` revisions rerun the same algorithm and retain the earlier result; they do not claim a new algorithm. A future algorithm must register another implemented version. No CLIP/image embeddings are recomputed by this extractor.

GET `/feedback/assets/{id}/visual-features` returns bounded history and overrides. POST its `/extract` child queues work. POST `/override` accepts `{featureId,value,reason,user}`. The referenced observed feature must belong to the asset, and the correction must match its type. `visual_feature_overrides` preserves original feature/value, correction, actor, reason and timestamp. Dataset snapshots resolve the latest correction by semantic attribute key across extraction revisions, so re-extraction cannot erase the correction. Requested values remain unmodified. Changing a taxonomy key's meaning is a new semantic key, not an excuse to reinterpret corrections.
